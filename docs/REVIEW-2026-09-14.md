## 🔴 追加发现（已修复）

### 头像存的是本地临时路径，跨设备/跨用户根本加载不出来

`src/pages/mine/mine.vue:147-150`：

```js
function onChooseAvatar(e) {
  userStore.patchLocal({ avatarUrl: e.detail.avatarUrl })
  saveProfile()          // 直接把临时路径存进了 users.avatarUrl
}
```

`e.detail.avatarUrl` 是 `chooseAvatar` 返回的**本地临时路径**（真机上是 `wxfile://tmp_xxx`，
开发者工具上是 `http://tmp/xxx`），**没有上传到云存储**。后果：

- 只在本机本会话有效，**重启小程序后自己的头像就没了**；
- 店主在订单列表里看别人头像时，拿到的是对方设备上的临时路径，**必然加载不出来**；
- 对比：菜品图是老老实实 `wx.uploadFile` 传到云存储再存 fileID 的（`admin/dishes/dishes.vue`），
  头像这条路漏了。

**已修复的版本**：

```js
async function onChooseAvatar(e) {
  const tmpPath = e.detail.avatarUrl
  if (!tmpPath || uploadingAvatar.value) return
  uploadingAvatar.value = true
  try {
    const r = await uploadFile(makeCloudImagePath('avatars', tmpPath), tmpPath)
    userStore.patchLocal({ avatarUrl: r.fileID })   // 存 cloud:// fileID，跨设备可用
    await saveProfile()
  } catch (err) { /* 提示上传失败，不写库 */ }
  finally { uploadingAvatar.value = false }
}
```

**顺带补上的服务端白名单**：之前 `user.updateProfile` 刻意没有校验 `avatarUrl` 协议，
正是因为当时客户端传的就是 `wxfile://`，加了会把「换头像」直接改坏。
现在客户端改走云存储了，白名单顺势补上（`cloud://` / `https://` 之外的值**丢弃但不算错**，
理由见上文「头像问题的修法」）。

**菜品图不受影响** —— `admin/dishes/dishes.vue` 本来就是 `wx.cloud.uploadFile` → 存 fileID，
和头像不是同一个问题。但它取扩展名用的是 `filePath.split('.').pop()`，
真机上 `wxfile://tmp_xxx` 未必带扩展名，那样会把整条路径拼进云存储路径；
已一并改用 `utils/image.ts` 的白名单提取器（属加固，不是修 bug）。

## 🔴 P0-1 订阅消息推送从未生效（守卫恒为真）

### 证据

`cloudfunctions/api/index.js:7` 定义常量：

```js
const SUBSCRIBE_TEMPLATE_ID = '9c7BsTLl1hL6bIAJ00J9c36A-NV-KREvOdnyGJvNklg'
```

`cloudfunctions/api/index.js:37-38` 的守卫：

```js
async function notifyOwner(items, orderId, orderer) {
  if (!SUBSCRIBE_TEMPLATE_ID || SUBSCRIBE_TEMPLATE_ID === '9c7BsTLl1hL6bIAJ00J9c36A-NV-KREvOdnyGJvNklg') return
```

两处字面量**经字节级比对完全相同**（长度均为 43，去重后只剩 1 个）→ 该条件**恒为真** →
`notifyOwner()` 每次都在第 38 行直接 return，第 49 行的
`cloud.openapi.subscribeMessage.send({...})` **永远不会被执行**。

### 影响

1. 朋友下单后，**店主永远收不到新订单提醒**；
2. `orders.notified` 永远停留在 `false` —— 而 `api/index.js:35-36` 的注释写着
   「前端据此展示『未通知』横幅，引导店主补一次授权」，但 `notified`
   在 `src/` 里**只出现在 `types/api.ts:58` 的类型定义中，没有任何 UI 读取它**，
   这个横幅压根没实现；
3. `src/utils/subscribe.ts` 里那套订阅授权（含「一次授权换一次推送」「别放在 await 之后」
   等精心处理）**全是白做的**；
4. 文档与实际情况不符，属于对外承诺错误：
   - `diancan-miniprogram/README.md:9`「朋友完成下单时，店主会收到**微信订阅消息**通知」
   - `README.md:151` FAQ 还在教「怎么排查收不到推送」，实际根因就是这段死代码
   - `diancan-uniapp/README.md:318` 的核对项「店主能收到订阅消息推送」一直没勾

### 推测成因

`if (!ID || ID === 某占位符) return` 这个守卫的本意应该是「**模板 ID 还没配好就别发**」，
最初比较的多半是 `'your-template-id'` 之类的占位串；后来把常量填成真实 ID 时，
忘了同步改守卫，于是它退化成了恒真式。常量与守卫被写成两处独立字面量，是这个坑的根源。

### 建议修法

把「是否已配置」和「模板 ID 是什么」解耦，只留一处字面量：

```js
// 用环境变量注入，避免同一串 ID 在仓库里出现 4 次（前端 config + 云函数常量 + 守卫）
const SUBSCRIBE_TEMPLATE_ID = process.env.SUBSCRIBE_TEMPLATE_ID || ''

async function notifyOwner(items, orderId, orderer) {
  if (!SUBSCRIBE_TEMPLATE_ID) return   // 只有「没配」才跳过
  ...
}
```

⚠️ 修完有个**连带改动必须一起做**：`order.create` 里是
`await notifyOwner(...)`（`api/index.js:211`）。现在它秒返回所以无感，
修好后推送会真的发出去、耗时数百毫秒，**会把下单响应拖慢**。
建议改成不 await（`.catch(() => {})` 吞掉），下单立即返回，推送在后台跑。

⚠️ 第二次连带：真机验证前先确认店主的订阅额度还在（订阅消息是「一次授权一次推送」），
否则会返回 43101 错误 —— 该错误现在被 `catch` 吞掉只打日志，属预期行为。

## 🟠 P1-1 点餐热力图统计被 100 条上限截断

### 证据

`api/index.js:234-248`：

```js
case 'stats.heatmap': {
  if (!isOwner) return { code: 403, msg: '无权限' }
  const days = Math.min(365, Math.max(30, event.days || 180))
  const since = new Date(Date.now() - days * 86400000)
  const res = await db.collection('orders')
    .where({ createdAt: _.gte(since) })
    .get()          // ← 没有 .limit()
```

前端 `src/pages/mine/mine.vue:78` 请求的是 `{ days: 180 }`（半年）。

### 为什么是 bug

微信官方文档明确：**云函数端未指定 `limit` 时，默认且最多取 100 条记录**
（小程序端是 20 条）。所以这行 `.get()` **最多只能拿到最近 100 笔订单**。

### 影响

- 订单总数超过 100 之后，热力图会开始**静默失真**：只有最近 100 单的分布是对的，
  更早的日期格子会无故变空；而且**不会报错**，只会「悄悄变少」，很长时间内不易察觉。
- 热力图按 26 周（约半年）渲染，正好和「180 天 / 100 条」形成矛盾。

### 建议修法

两个方向，任选：

1. **分批取全量**（改动最小，保持现有前端结构）：

```js
const MAX = 100
const total = (await db.collection('orders').where({ createdAt: _.gte(since) }).count()).total
const times = Math.ceil(total / MAX)
const tasks = []
for (let i = 0; i < times; i++) {
  tasks.push(db.collection('orders').where({ createdAt: _.gte(since) }).skip(i * MAX).limit(MAX).get())
}
const res = await Promise.all(tasks)   // 再合并 flat
```

2. **改成聚合按天 group**（更优雅，但要确认聚合对 `createdAt` 做日期分组时区是否与本地一致，
   云函数默认 UTC，现有代码用 `getFullYear/getMonth/getDate` 是**服务器本地时区**，
   聚合表达式处理时区容易踩坑）。**保守起见建议先走方案 1。**

## 🟡 P2 权限与健壮性

### P2-1 `invite.accept` 存在竞态，邀请码可被重复使用

`api/index.js:171-185`：先 `where({ code }).get()` 判断 `used`，再 `update` 置 `used: true`，
**两步之间不是原子的**。两个访客同时提交同一邀请码 → 都读到 `used: false` → 都通过。

熟人场景下危害有限（两人本来都拿到了这个码），但 `used` / `usedBy` 记录会失真，
且「一码一人」的语义不成立。

**修法**：改成条件更新并校验影响行数：

```js
const r = await db.collection('invitations').where({ code, used: false })
  .update({ data: { used: true, usedBy: OPENID, usedAt: db.serverDate() } })
if (r.stats.updated !== 1) return { code: 400, msg: '该邀请码已被使用' }
// 只有 updated === 1 才继续给用户升 role
```

### P2-2 邀请码无查重、无有效期

`api/index.js:15-20` 的 `genCode()` 用 `Math.random()` 生成 6 位码，**不检查是否已存在**。
而 `invite.accept` 用 `where({ code }).get()` 只取 `data[0]` —— 一旦重码，
被遮蔽的那个码**永久不可用**，且无法排查。

同时**没有任何有效期**，店主发出去的码永久有效。

**修法**：生成时 `count()` 查重重试（最多 3 次）；给邀请码加 `expiresAt`，
接受时校验过期。32 个字符取 6 位约 10.7 亿组合，碰撞概率低但不为零，且成本极低。

### P2-3 `order.create` 对 items 零校验

`api/index.js:188-213`：

- `it.quantity` **完全不校验**。客户端可传 `999999` 刷爆 `orderCount`
  （`_.inc(it.quantity)` 会照单全收），甚至可传负数把别人的统计打回去；
- `items` **数组长度无上限**，而第 205-209 行对每个 item 都做一次 `await` 数据库更新 →
  提交一个几千项的数组就能让云函数连续打几千次库（超时 / 烧配额）；
- `it.name` 直接落库，无长度截断。

**修法**：入库前归一化 —— 数量取 `1~99` 的整数、`items` 上限 50 条、
`name` 截断到 20 字、`dishId` 校验存在性。

### P2-4 店主身份可被「自动晋升」（`login/index.js`）

两处逻辑叠加：

- `login/index.js:26-27`：新用户登录时若系统里没有 owner，**当前用户直接成为 owner**；
- `login/index.js:15-21`：老用户是 `guest` 且系统里无 owner 时，**自动晋升为 owner**。

这是刻意设计的「自愈」，在单人开发时很方便。但副作用是：
**一旦店主那条 user 记录被误删（或在云开发控制台里清库重来），
下一个打开小程序的任意访客就会静默变成店主**，拿到全部管理权限。

**修法**：把店主 openid 固定到云函数环境变量（`OWNER_OPENID`）做白名单，
自动晋升时只认这一个 openid；或至少在晋升时写入一条显眼的审计日志。

### P2-5 入参缺少取值校验

- `api/index.js:227-231` `order.updateStatus`：`event.status` 是任意字符串，无白名单校验
  （应限定 `pending` / `done` / `canceled`）；
- `api/index.js:80-87` `user.updateProfile`：`nickname` 无长度上限，可写入超长字符串。

危害不大（展示层会转义，小程序无 XSS 面），但属明显的边界缺失，顺手补掉成本极低。

### P3-1 ⭐ 数据库集合权限（最需要确认的一条）

好消息：客户端 `src/` 里**没有任何 `cloud.database()` / `.collection()` 调用**
（已 grep 确认），所有数据都走云函数 —— 这是非常正确的做法。

但它的安全性**完全依赖后台权限设置**。请去
云开发控制台 → 数据库 → 权限设置，确认以下 5 个集合**都是「仅管理端可读写」**：

`users` / `orders` / `dishes` / `categories` / `invitations`

如果其中任何一个是「所有用户可读」或「所有用户可写」，那么熟人里的任何一个人
都可以用开发者工具直接读走**全部用户的 openid、昵称、头像**，甚至直接改自己的 `role` 为
`owner` —— 云函数里那套严密的 `isOwner` 检查会被整个绕过。

### P3-2 云存储权限

菜品图存在云存储 `dishes/` 目录（`admin/dishes/dishes.vue` 的 `uploadImage`）。
确认存储权限不是「所有用户可写」，否则任何人可往你的云存储桶里塞文件（费用算你的）。

### P3-3 `sitemap.json` 允许被微信索引

两版的 `sitemap.json` 都是：

```json
{ "rules": [{ "action": "allow", "page": "*" }] }
```

意味着这个小程序**可以被微信搜一搜索引到**，陌生人能搜到「呼噜点餐」并进入（落到访客态）。
对一个「朋友圈熟人私房菜」来说这多半不是想要的。

**建议**：改成 `"action": "disallow"`（或至少把管理页 `pages/admin/*` 排除）。

### P3-4 用户隐私保护指引未声明

项目用到了两类需要声明的能力：

| 用到的地方 | 涉及的信息 |
| --- | --- |
| `mine.vue:214` `open-type="chooseAvatar"` | 用户**头像** |
| `dishes.vue:183` `uni.chooseMedia` | **相册 / 摄像头** |
| `users` 集合存 `nickname` / `avatarUrl` | 用户**昵称** |

需要在 mp 后台 → 设置 → 服务内容与声明 → **用户隐私保护指引**里勾选对应项。
没声明的话，这些能力在真机上会被拦截（头像选不了、图片传不了）。

### P3-5 类目与 ICP 备案

上一轮已确认（2026-09 核实）：**个人主体不开放「线上点餐 / 外卖」类目**，
个人主体走不了正式发布；2023-09 起小程序上线前还必须完成 ICP 备案。
如果是个人主体，现实路径就是体验版（且体验成员按主体只有 15 个名额）。

## ⚪ P4 一致性与视觉

### P4-1 导航栏对比度违背自家设计规范

`pages.json` → `globalStyle`（原生版 `app.json` 同样）：

```json
"navigationBarBackgroundColor": "#F5A623",
"navigationBarTextStyle": "white"
```

白字压在 `#F5A623` 上的对比度约 **2.0:1**，远低于 WCAG AA 的 4.5:1。

**这是自相矛盾的**：项目设计系统里明确写着
「禁用橙底白字（对比不达标）」，所有 CTA 都改成了「黄橙渐变底 + 深棕粗体字」，
唯独导航栏漏改了。

**最小改动**：`"navigationBarTextStyle": "black"`（黑字对比度约 **10.4:1**）。
不用动背景色，视觉上仍然协调。

### P4-2 uniapp 工程缺 `.gitignore`

`diancan-miniprogram/.gitignore` 存在，`diancan-uniapp/` **没有**。
两个目录目前都不是 git 仓库，所以现在没造成损失；
但一旦把 uniapp 纳入版本管理，`node_modules/` 和 `dist/`（含 476KB 产物 + 软链接）
会被一起提交进去。

**建议**：把原生那份 `.gitignore` 复制过去，再补上 `dist/`。

## 做得好的地方（别改坏）

审查中确认这些设计是对的，后续改动请保持：

1. ⭐ **权限校验全在服务端**。`api/index.js` 的 18 个 action 里，凡涉及写操作或店主数据的
   （category/dish 的增删改、`invite.create/list`、`order.listAll/updateStatus`、
   `stats.*`）**每一个都有 `if (!isOwner) return { code: 403 }`**，
   前端隐藏按钮只是 UX，不承担安全职责。这个边界划得很干净。
2. ⭐ **openid 取自 `cloud.getWXContext()`，从不信任客户端传参**。
   订单归属、邀请码使用记录都用服务端拿到的 OPENID，客户端无法伪造身份。
3. **客户端零直连数据库**，全部走云函数 —— 攻击面小，也让 P3-1 一旦配对就是安全的。
4. `order.create` 校验了 `role === 'guest'` 的拦截（未接受邀请不能下单）。
5. `clampRating()` 把评分夹在 0~5 且按 0.5 步进，不信任客户端。
6. 前后端 **18 个 action 完全对齐**（已逐一比对，无孤儿 action、无漏实现）。
7. 全仓库**无 TODO/FIXME 残留**，**无硬编码密钥**（无 `.env` / `.pem` / secret 文件）。
